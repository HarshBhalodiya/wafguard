# Phase 9 Report — Continuous integration

Date: 2026-10-13 · Plan: `docs/phase9_plan.md` (P9-1…P9-6, all delivered) · Decisions: D-044 in `docs/DECISIONS.md`

Phase 9 ran the first thing a CI gate should protect it from: what happens on a clean checkout
with nothing pre-seeded. The answer to that question was the phase — the workflow file
(.github/workflows/ci.yml) was written *after* the answer was verified local, and the
workflow's prep steps were re-verified against the venv/install results of that clean run.

## Verified on a bare checkout (P9-1 audit)

- **Checkout:** `git ls-files -co --exclude-standard -z | tar | mkdir sim && git init && git add -A && git commit` — 265 tracked/untracked-unignored files; exactly what CI's `actions/checkout` + the repo's gitignore would see on a push (minus `.gitignore`-ignored items). Python = standalone 3.13.15 from `uv` (no system python used).
- **`pip install -r requirements.txt`:** exit 0; **24m13s wall** (torch dominates). Used `uv` for the venv creation credentialing, but the workflow's install is ordinary `pip`/`python -m pip`, matching the clean-state semantics.
- **`scripts/download_secom.py`:** exit 0; **13s**; writes `data/secom/secom.data` + `secom_labels.data` from the public UCI zip — no credentials, no login, deterministic archive contents (`secom.names` stays as metadata, not a label file).
- **`scripts/train_wafer_model.py`:** exit 0; **50s**; trains the wafer CNN artifact to `backend/models/artifacts/` so `def get_wafer_bundle()` has something to load (the gap it raises `ModelUnavailableError` for without this step). Procedural synthetic maps, 9 classes, seed 99, 300/class — exactly what `adversarial` renders in the comparison scripts; no download.
- **`pytest tests/ -q`:** exit 0; **5m07s**; **169 passed, 1 warning**. The sole failure-mode possibility remaining for CI is a runner that cannot install from PyPI at all (network outage) or that blocks the pip npm cache — both are infrastructure, not repo bugs; the suite itself is unchanged and all 169 tests pass.
- **plaintext `.env` check (pre-existing D-003 already applied):** `.gitignore` keeps `.env` out of tracks; the secret-scan suite asserts `.env` is not tracked and that no credential-shaped string matches anywhere in tracked files — already green for the full Phase 1–8 work, and P9-3 gives it a dedicated CI job.
- **No test was skipped, weakened, or changed in this phase.** The 169 suits are exactly the same as at Phase 8 handoff (155 + 14 Phase-8 additions). The only file-level changes were repo-native fixes of the audit findings (`.gitignore`, the vite temp deletion) and the new workflow + report + decision files.

## Honest limits

- **CI verifies a workflow file, not a workflow run.** This phase validated the repo side of the question — what a clean checkout sees and whether the two suites + build can run without secrets or services — and wrote the workflow as the gate that enforces it, plus a fast-fail secret scan. The first real proof of the gate is the first push that runs it; the report states which part was verified and which was not (dashboard vs. on-repo verification).
- **No badge is claimed green this turn.** The README section's badge is a placeholder + a documented replacement rule, because the workflow has not yet run on GitHub and inventing a green badge before the first real run would be exactly the "claim but don't verify" pattern Phase 0 flagged.
- **Scope is hermetic-only, by design.** CI runs the two suites + build + the secret gate. Mongo-touching pipeline stages (seed, train-with-backfill, `build_dataset.py --all`) are explicitly not CI — they touch shared state and require a reachable cluster + credentials beyond what a public repo can host (D-014/D-036 lineage). The README and workflow comment say so, and neither implies otherwise.
- **Python 3.13 in CI vs 3.14 on local dev machines** is a stated divergence (D-001), chosen for the README-validated wheels for torch/xgboost/shap, with `uv` used only for this local Python-3.13 fetch — not for anything CI does.
- **No lint/type/coverage gates** — the repo has none configured, so none added; adding one is new surface beyond this to-do, and kept for a future phase if the user re-cuts.
